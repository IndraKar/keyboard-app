# Deploying the Keyvoria API and switching on Stripe

Start to finish, roughly 45 minutes. Do the whole thing in **test mode** first —
no real card is charged until you deliberately swap the keys in step 8.

Everything below is yours to do: it needs your Stripe account and your hosting
account, and neither can be created on your behalf.

---

## 1. Stripe account and the price

1. Create an account at **dashboard.stripe.com**. Leave the toggle on **Test
   mode** for now.
2. **Product catalogue → + Add product**
   - Name: `Keyvoria Premium`
   - Price: **5.95 USD**, **Recurring**, **Monthly**
3. Save, then open the price and copy its id. It starts with **`price_`**.
   > A `prod_` id is the *product*, not the price. The server needs the
   > `price_` one; the `prod_` one produces "No such price" at checkout.
4. **Developers → API keys** → copy the **Secret key** (`sk_test_…`).

## 2. Deploy on Render

`render.yaml` sits at the **repository root** — Render looks for it there and
nowhere else — and describes the web service and the database together.

1. **render.com → New → Blueprint**, connect GitHub, pick
   `IndraKar/keyboard-app`, branch `KeyboardApp`.
2. Render reads `render.yaml` and shows two resources: **keyvoria-api** and
   **keyvoria-db**. Choose the plans you want; the blueprint deliberately does
   not pin them, because Render's plan names change and a wrong one makes the
   whole blueprint fail to parse.
3. It asks for the values marked `sync: false`. Leave `STRIPE_WEBHOOK_SECRET`
   blank for now — it does not exist until step 5 — and fill in the rest from
   step 1.
4. **Apply**. The first build takes a few minutes.

The tables create themselves on first boot: the blueprint sets
`KEYVORIA_AUTO_MIGRATE=1`, and every statement in `schema.sql` is
`IF NOT EXISTS`, so it is a no-op on every boot after the first. If the schema
cannot be applied the service **refuses to start** rather than serving requests
against tables that are not there.

To run it yourself instead, from anywhere with Node:

```bash
DATABASE_URL="<external connection string>" npm run migrate
```

No `psql` needed — it goes through the same `pg` driver the server uses.

### A note on free plans

A free Render web service spins down after inactivity and takes up to a minute
to wake. Stripe retries a failed webhook for up to three days, so a payment
arriving at a sleeping service is eventually recorded rather than lost — but the
customer waits on the app meanwhile. Free Postgres instances also expire. For
anything taking real money, use paid plans.

### Deploying somewhere else

The `Dockerfile` is self-contained and takes the same environment variables:

```bash
docker build -t keyvoria-api -f server/Dockerfile server
docker run -p 8787:8787 --env-file server/.env keyvoria-api
```

Fly, Railway, Cloud Run and ECS all take it as-is. The only requirements are a
public HTTPS URL and the variables below.

## 3. Your API address

Render gives the service a URL like `https://keyvoria-api.onrender.com`. Check
it:

```bash
curl https://keyvoria-api.onrender.com/health
# {"ok":true,"service":"keyvoria","milestones":["M7","M7a"]}
```

That URL is what Stripe posts to in step 5 and what goes into the app in step 7.

## 4. Environment variables

| Variable | Value |
| --- | --- |
| `NODE_ENV` | `production` |
| `DATABASE_URL` | filled in by Render from the blueprint |
| `KEYVORIA_SESSION_SECRET` | generated by Render. Changing it signs everyone out. |
| `KEYVORIA_AUTO_MIGRATE` | `1` — creates the tables on boot |
| `STRIPE_SECRET_KEY` | `sk_test_…` from step 1 |
| `STRIPE_PRICE_ID` | `price_…` from step 1 |
| `STRIPE_WEBHOOK_SECRET` | step 5 |
| `GOOGLE_CLIENT_ID` / `GOOGLE_CLIENT_SECRET` | step 4a — without both, Google sign-in is off |
| `YAHOO_CLIENT_ID` / `YAHOO_CLIENT_SECRET` | step 4a — without both, Yahoo sign-in is off |
| `KEYVORIA_ALLOWED_ORIGIN` | your site's origin, e.g. `https://keyvoria.com` |
| `KEYVORIA_SUCCESS_URL` | where Stripe returns after payment |
| `KEYVORIA_CANCEL_URL` | where Stripe returns if they back out |

**Never set `KEYVORIA_DEV_AUTH` or `KEYVORIA_ALLOW_UNSIGNED_WEBHOOKS` in
production.** The first lets anyone be any user; the second lets anyone who
finds the URL give themselves a subscription. The server prints an error on
every boot if it catches either one in production.

## 4a. Sign in with Google and Yahoo

**Nobody can create an account until this is done.** The app works without it —
people can play everything — but their progress is not saved anywhere they can
get it back from. The server prints a warning on every boot while sign-in is
unconfigured.

A provider needs **both** halves. With only one, the server leaves that provider
switched off and says so at boot, rather than showing a button that fails at the
consent screen.

### The redirect URI

Both consoles ask for it, and it must match **character for character**,
including `https` and no trailing slash:

```
https://<your-render-url>/v1/auth/google/callback
https://<your-render-url>/v1/auth/yahoo/callback
```

e.g. `https://keyvoria-api.onrender.com/v1/auth/google/callback`.

A mismatch here is the single most common failure, and the provider's error
(`redirect_uri_mismatch`) names it plainly. If you later put the API on your own
domain, the registered URI has to change with it.

### Google

1. <https://console.cloud.google.com/> → create a project (or pick one).
2. **APIs & Services → OAuth consent screen**. External. Fill in the app name,
   your support email, and a developer contact. Scopes: just `openid`, `email`
   and `profile` — all three are default, so you do not need to add any.
3. While the consent screen is in **Testing**, only accounts you list as test
   users can sign in. Add yourself. To let the public in, **Publish app**;
   because you are requesting only these three basic scopes, that does not
   require Google's security review.
4. **Credentials → Create credentials → OAuth client ID → Web application**.
5. Under **Authorised redirect URIs**, add the Google URI above.
6. Copy the client ID and client secret into `GOOGLE_CLIENT_ID` and
   `GOOGLE_CLIENT_SECRET`.

### Yahoo

1. <https://developer.yahoo.com/apps/> → **Create an App**.
2. Application type **Web Application**.
3. **Redirect URI(s)**: the Yahoo URI above. Yahoo rejects plain `http` and
   rejects `localhost`, so you cannot test Yahoo against a local server — it has
   to be the deployed HTTPS URL.
4. Under **API Permissions**, tick **Profiles (Social Directory) → Read Public**,
   which is what grants `openid`, `email` and `profile`.
5. Copy the Client ID (Consumer Key) and Client Secret (Consumer Secret) into
   `YAHOO_CLIENT_ID` and `YAHOO_CLIENT_SECRET`.

### Check it

```bash
curl https://<your-render-url>/v1/auth/providers
# {"providers":[{"id":"google","label":"Google"},{"id":"yahoo","label":"Yahoo"}],"configured":true}
```

Whatever is listed there is what the app offers. If a provider is missing, its
two variables are not both set.

### What the server does with a sign-in

The browser only ever opens a window at **your** server. The server redirects to
Google or Yahoo, receives the authorization code, exchanges it for an ID token
**server-side with the client secret**, and verifies that token's signature
against the provider's published keys before believing a word of it. The client
secret never reaches the browser, and no password ever reaches Keyvoria.

What comes back to the app is a Keyvoria session token, collected through a
single-use ticket. The token is never put in a URL or in the page.

## 5. The webhook

This is the step everything else depends on: **without it, people pay and the
server never finds out.**

1. **Developers → Webhooks → Add endpoint**
2. URL: `https://your-api-host/v1/webhooks/stripe`
3. Select these events:
   - `checkout.session.completed` — creates the subscription
   - `invoice.payment_succeeded` — renews it
   - `invoice.payment_failed` — starts the grace period
   - `customer.subscription.updated` — cancel / uncancel
   - `customer.subscription.deleted` — expiry
4. Copy the **Signing secret** (`whsec_…`) into `STRIPE_WEBHOOK_SECRET` and
   redeploy.

## 6. Check it works, with no money involved

```bash
curl https://your-api-host/health
# {"ok":true,...}
```

Then, with the Stripe CLI:

```bash
stripe login
stripe listen --forward-to localhost:8787/v1/webhooks/stripe
stripe trigger checkout.session.completed
```

`stripe listen` prints its own `whsec_…` — use that one while forwarding
locally.

A full test purchase: start a checkout from the app, and on Stripe's page use
card **4242 4242 4242 4242**, any future expiry, any CVC, any postcode. Then
check the subscription exists:

```bash
curl -H "Authorization: Bearer <session token>" https://your-api-host/v1/subscription
```

## 7. Point the app at it

The app already speaks to this server — there is no code to write.

**Profile → Server → API address**: your deployed URL, e.g.
`https://keyvoria-api.onrender.com`. Tap **Connect**. The card then reads
"Connected. Sign in with Google or Yahoo to save your progress."

Then **Sign in** offers whichever providers step 4a configured. Signing in gets
a session token automatically — there is no token to paste any more.

To skip the address entirely for everyone, set `DEFAULT_API_BASE` near the top of
`prototype/keyvoria-playable.html` to your URL. Then the app points at your
server out of the box and people only ever see **Sign in**.

From that point the server, not the app, decides who has paid. **Subscribe** calls
`/v1/billing/checkout`, opens Stripe's hosted page in a new tab, and the app polls
until your webhook confirms the payment — then it unlocks on its own, with no
reload. Cancel and resume go through the server too, which tells Stripe before
recording anything locally.

Leave those fields empty and the app runs entirely on the device with the
simulated checkout, which refuses real cards. That is the right mode for showing
the app to someone without a server in front of it.

`npm run token` still exists for poking at the API from a shell without a
browser. It mints a token for an arbitrary user id with no account behind it,
so **it is a password** — do not paste one anywhere public. Normal users never
see one.

## 8. Going live

1. Flip the dashboard to **Live mode**.
2. Recreate the product and price there — **test and live objects are separate**,
   so the test `price_` id does not exist in live mode.
3. Swap in the `sk_live_…` key and the live price id.
4. Add the webhook endpoint again in live mode and swap in its new `whsec_…`.
5. Stripe needs your business details and a bank account before it will pay out.

The server prints `stripe: LIVE KEYS — real charges` on boot when live keys are
in use. If you see that unexpectedly, stop.

## What breaks this, in order of how expensive it is

**No `DATABASE_URL`.** The server falls back to an in-memory store and forgets
every subscription on the next restart — a deploy, a crash, the host moving the
container. People would pay and silently lose access, and Stripe never resends
the webhooks that would rebuild it. The server logs this as an error on every
production boot. Do not ignore it.

**No `STRIPE_WEBHOOK_SECRET`.** Signed deliveries are rejected, so no payment is
ever recorded. Everyone pays and nobody gets Premium.

**Wrong webhook URL.** Same outcome, and Stripe will show the failures under
Developers → Webhooks. Check there first when a test purchase does not appear.

**`price_` vs `prod_`.** Checkout fails with "No such price".

**Forgetting step 8.2.** Live mode cannot see test-mode prices.

## What is not built yet

- **PayPal** is modelled end to end in the subscription logic, but its webhook
  signature scheme (a certificate chain, not a shared secret) is not
  implemented. That endpoint returns **501** rather than trusting an unverified
  delivery.
- **Apple and Google in-app purchase** are modelled for cancellation and
  renewal, but their receipt verification is not written. You only need them if
  you ship in the app stores, where they are mandatory and take 15–30%.
- **Account deletion cancels the subscription first, and refuses if it cannot.**
  `DELETE /v1/account` cancels at Stripe before removing anything, and returns
  502 without deleting if that call fails. Deleting our record of a live
  subscription would not stop the card being charged — it would only destroy
  the evidence that it was happening. A subscription bought through Apple or
  Google is refused outright with an explanation, because we cannot cancel
  those on the user's behalf.
- **Signing out does not revoke a token.** Session tokens are stateless HMACs
  with no server-side record, so signing out ends the session on that device by
  discarding the token — it does not invalidate one already copied elsewhere.
  The token expires on its own after 90 days. Real revocation needs a denylist
  keyed on the token's `jti`, which is a change to `verifyToken`.
- **Deleted data is deleted, not archived.** There is no soft-delete and no
  recovery window: a deleted account's progress is gone. That is the honest
  reading of what the button says, and it is what the GDPR and several US state
  laws ask for, but it does mean support cannot undo it for someone who
  regrets it.
- **Tax.** Digital subscriptions are taxable in many US states and carry VAT in
  the EU/UK. Stripe Tax handles calculation; a merchant of record such as Paddle
  handles calculation *and* filing. Neither is wired up here.
